## 14.07.2026 — правки доверителя в `.docx` молча затёрты пересборкой из скрипта, выжили только в `_baselines/`

Доверитель по ходу сессии открывал уже выданные `.docx` (`prikaz-2-sluzhebnaya-proverka_v1`, `uvedomlenie-bilalov_v1`, `uvedomlenie-bank-alfa_v1`, `instrukcia-dlya-bilalovoy_v1`) и правил их напрямую в Word/аналоге — не через чат. Пока файл был открыт у него, `create_docx.py`'s `DocBuilder.save()` пытался перезаписать `_baselines/<имя>.docx` через `shutil.copy2` и ловил `OSError` (файл занят другим приложением) — исключение проглочено (`except OSError: pass`), без предупреждения в лог/чат. В результате: рабочий файл в `03_drafts/` перезаписался моим свежим прогоном (правки доверителя исчезли из него), а его правки уцелели только в `_baselines/` — то есть папка «снимок ДО» внезапно стала единственным местом, где лежит «ПОСЛЕ». Обнаружено случайно, только благодаря `cp:lastModifiedBy`/`cp:revision` в `docProps/core.xml` каждого `.docx` (у нетронутых файлов пусто и revision=1, у правленых — «Filipp doveritel» и revision 2-3): без этой проверки я бы принял направление diff'а наоборот и приписал доверителю правки, которые на самом деле были моими собственными более ранними черновиками.

- **Причина:** пересборка документа из Python-скрипта поверх уже выданного и потенциально открытого доверителем файла — без проверки, не изменился ли файл с момента выдачи, и без видимого сигнала при сбое копирования baseline.
- **Исправлено (в этой сессии):** проверил `docProps/core.xml` (`lastModifiedBy`/`revision`) каждого затронутого `.docx`, чтобы понять реальное направление правки прежде чем читать diff; перенёс найденные правки в `redlines.md`, руками применил их к мастер-версиям.
- **Системное правило:** перед тем как пересобирать/перезаписывать уже выданный `.docx` из скрипта (а не через `Edit`), сначала сравнить его текущее содержимое с последним известным моим выводом (или с `_baselines/`, если он не тронут). Если отличается — считать это правкой доверителя, не перезаписывать вслепую, сначала спросить или слить правки. И: `except OSError: pass` в `create_docx.py.save()` — тихий отказ снимка недопустим, минимум печатать предупреждение в stdout при сбое копирования baseline, иначе несовпадение обнаруживается только случайно (как здесь — через ручную проверку XML-метаданных).

## 23.07.2026 — внешняя апелляционная жалоба содержала выдуманную опору на КС РФ; анонимизация совета читается по стилю

## 25.07.2026 — битый текст-слой PDF читался как настоящий; роутер отдавал кашу вместо реквизитов

По делу doveritel-2/neosnovatelnoe-obogashchenie-2026 материалы пришли одним PDF на 28 листах со «своим» текстовым слоем: кто-то прогнал скан через чужой OCR и запек результат в файл. `markdown_extract.py` увидел 27 текстовых страниц из 28, выбрал маршрут text-pdf и выдал кашу вида «Рссn)'6л~1кс», «Эар111tч11111», «l'ap:ii\1111111•». Фамилия истца, номера дел, суммы — все нечитаемо. Пришлось вручную рендерить страницы в PNG и прогонять Apple Vision.

- **Причина:** роутер измерял только КОЛИЧЕСТВО символов на странице (`TEXT_MIN`), но не их КАЧЕСТВО. Битый слой хуже отсутствующего: он проходит все проверки и врет в реквизитах, а не падает.
- **Исправлено в коде:** `text_layer_ok()` + `pdf_garbage_pages()` — метрика доли латиницы среди букв (порог 10%), «русский ли документ» считается по всему файлу, а не по странице (постраничная проверка пропускала худшие листы как «иноязычные»). Битых листов больше четверти — весь PDF идет на переOCR. В note добавлено предупреждение «БИТЫЙ ТЕКСТ-СЛОЙ». Проверено: спорный PDF теперь дает 28 из 28 страниц через Apple Vision (56 468 символов чистого текста), чистые PDF других дел маршрут не меняют.
- **Системное правило:** любой сомнительный текст из первички проверять на осмысленность до работы с ним, а не после. Признак чужого запеченного OCR — латиница внутри русских слов. Ложное срабатывание детектора стоит минуты OCR ($0), пропуск — ошибки в судебном документе.

## 02.08.2026 — Пилот Unlimited-OCR: MLX-порт непригоден

**Что проверяли.** Открытую OCR-модель `baidu/Unlimited-OCR` (MIT, 3,3 млрд параметров,
OmniDocBench 93,23%) как замену Apple Vision на страницах со сложными таблицами.
Повод: Apple Vision разрушает структуру таблиц, а у Раковца по таблицам заключения
эксперта (стр. 82-83) считались остатки счетов — там таблица есть доказательство.

**Результат: ОТКЛОНЕНО.** Порт `LoJexLLM/Unlimited-OCR-MLX` (6,2 ГБ, единственный
под Apple Silicon в fp16) не запускается. Найдено 11 дефектов подряд:

1. Относительный импорт без пакета — нужен симлинк `unlimited_ocr_mlx`.
2. `UnlimitedOCRConfig(**config)` вместо `from_original_config`.
3. Ключи весов `sam_model.neck.N.*` против ожидаемых MLX `neck.layers.N.*`.
4. Отсутствует буфер `vision_model.embeddings.position_ids`.
5. Свёртки в раскладке PyTorch (O,I,H,W) вместо MLX (O,H,W,I).
6. `rel_pos` сайзится по полной сетке для ВСЕХ блоков; в весах оконные блоки 27,
   глобальные 127. Сопутствующе вскрылось: для оконных блоков порт вообще НЕ применяет
   relative position bias (8 из 12 блоков SAM) — то есть геометрия теряется by design.
7. `AutoTokenizer` уходит в remote-code через `auto_map` и падает.
8. Токенайзер без спецтокенов даёт `None` в `input_ids`.
9. `dtype=bool` вместо `mx.bool_`; `mx.array([ndarray])` — старый API.
10. `_interpolate_pos_embed` не сходится по формам (3 145 728 в (1,768,40,40)).
11. `.at[idx].set()` — метода НЕТ ни в одной версии MLX (там `.at[].add()`).

П. 11 доказывает: код не дрейфовал за API, он **никогда не исполнялся**. Порт
опубликован непротестированным.

**Правило на будущее.** Открытая модель с бенчмарком и звёздами ≠ работающий порт под
нашу платформу. Проверять надо не модель, а конкретный порт, и первым делом — запускается
ли он вообще на одной странице. Бюджет пилота ограничивать: 2-3 дефекта склейки чиним,
дефект в математике или несуществующий API — стоп, порт негоден.

**Что осталось.** Apple Vision остаётся движком по умолчанию (работает, $0, локально).
Задача «структура таблиц» НЕ решена и остаётся открытой. Кандидаты на следующий заход:
GGUF-сборки под llama.cpp (требуют неслитый PR #17400 — тоже хрупко), либо ждать
поддерживаемого порта. Окружение пилота: `~/.cache/themis-ocr` (7,5 ГБ), сносится
одной командой `rm -rf ~/.cache/themis-ocr`.
